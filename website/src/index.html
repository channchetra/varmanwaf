One control plane. A fleet of edges. Every request decided.

VarmanWAF is a distributed Web Application Firewall you run yourself: a central control plane, lightweight edge agents on Cloudflare Pingora, and a native security engine written in Rust. Every change is versioned, pushed to the edges, and verified by a 45-script end-to-end sweep.

What it does

Everything an operator needs, in one console

The console is the product: every surface is honest about what is published, what is applied, and what is deliberately not supported.

Protection

  • 14 built-in managed rules with anomaly scoring, paranoia gating and per-rule modes
  • Custom rules in a readable expression language, with a rule tester
  • Native SecLang: virtual patches, OWASP CRS 4.30.0 import, SecRuleUpdateTargetById / SecRuleRemoveById
  • Exclusion packages: curated per-app sets + upstream SecLang imports with an import report
  • API schema validation with per-operation Off / Observe / Enforce

Access & abuse control

  • IP rules and reusable IP groups
  • Geo and ASN policy from ipverse only - unsynced keys are shown as not enforced
  • Client IP analysis: what the edge would decide, using the same loaders
  • Rate limiting by IP, header, cookie, path, ASN or country
  • Bot posture, verified bots, challenges, under-attack mode

Fleet & delivery

  • Control plane + edge agents; the control plane is never in the request path
  • Versioned config bundles, config history with diff and rollback
  • Revisioned policies sites follow, with effective-posture resolution
  • Routing topology: the real request path as a live, editable graph
  • Agents, mTLS pinning, closed registration

Observability

  • Security events with a why resolver: rules, scores, exclusions
  • Access logs, analytics, top rules / IPs / paths
  • Alerts: rules, silences, email / webhook / Telegram delivery
  • Reports on demand with custom heading/footer and schedules
  • Auto-block ledger with immediate revocation

Console experience

  • Policy tuning surface: summary, site posture, effective posture, exceptions, packages, preview, history
  • API assets: observed inventory vs declared spec, bounded learning, OpenAPI draft
  • Display & data timezone honoured by reports and charts
  • Custom error pages, passkeys, API keys, dashboard users

Operations

  • High availability: edge fleets, control-plane standby, database HA
  • Sizing from measured numbers, with the storage-growth math
  • Backup / restore / rolling upgrade runbooks
  • Optional Elasticsearch log shipping
  • Everything documented - the website is generated from the repository docs

Architecture

The control plane is never in the request path

Traffic is served by the edges from local, persisted configuration. Losing the control plane or the database stops changes - never traffic. 

        Visitors / attackers / APIs
                  │
                  ▼
   ┌─────────────────────────────────────────────┐
   │  Varman Edge (Pingora + Varman engine)      │   :80 / :443
   │  canonicalise → evaluate → decide → proxy   │
   └───────────────┬─────────────────────────────┘
                   │ (allowed requests only)
                   ▼
        Origin pools → your servers

   ┌─────────────────────────────────────────────┐
   │  Control plane                              │
   │  REST API + console            :9080 (TLS)  │
   │  gRPC control protocol         :9090        │
   │  PostgreSQL (authoritative store)           │
   └─────────────────────────────────────────────┘
             ▲ gRPC: registration, heartbeat,
             │       config sync, log/metric/
             │       certificate shipping

Edge autonomy

Bundles, blocked IPs and config hashes persist on disk. An edge restarts from its last-good configuration and reconnects with backoff.

Versioned delivery

Every change compiles a bundle with a config hash, applies hot (no restart), and lands in config history with a diff and rollback.

Immutable snapshots

Per-site runtimes swap atomically behind ArcSwap: in-flight requests keep the snapshot they started on.

Deploy how you want

All-in-one for single servers, or control plane plus one agent per edge node behind your load balancer, DNS round-robin or anycast.

Security engine

One normalization. Many lanes. Honest verdicts.

Built-in managed rules

14 rules (VARMAN-1001..1061; 13 at Normal, one Strict-only) written in the same expression language as custom rules. Anomaly gates (SQLi / XSS / aggregate / RCE), recon and backup probes, scanner user agents, method policy, admin paths, Log4Shell.

  • Scoring: severity points; family sub-score ×12 - one critical hit = 60
  • Gates: rule paranoia ≤ site paranoia, stack scope, monitor lists
  • Advanced mode (Strict) tightens gates 60→50 / 80→70 and adds the RCE gate
Rule-by-rule detail →

OWASP CRS 4.30.0, natively

693 imported rules run on the built-in SecLang engine - no ModSecurity required. Rules the parser cannot compile stay visible with their error; nothing is dropped silently.

  • Paranoia ceiling: rules above it are not sent to the edge; unset keeps every compiled rule
  • Bind rulesets to policies; exclusion packages adjust them with SecRuleUpdateTargetById
  • Two separate knobs: site paranoia (managed rules) vs CRS ceiling (imported rules)
CRS & ceiling detail →

What it deliberately does not do

  • No invented success: an unsynced geo/ASN key, an uncompilable CRS rule, a not-applied setting is shown as such.
  • No value collection in learning: API learning reads structures and counts, never values.
  • No silent drops: pass-through 5xx is not access-logged; WAF answers are - and the docs say which is which.

Quick start

One command to a protected site

docker compose up -d
# console:  https://localhost:9080   (self-signed on first boot)
# traffic:  :80 / :443   ·   gRPC control: :9090
# login:    admin@varman.local / varman123   (change it immediately)
  1. Create a site and point it at your origin.
  2. Point DNS at the edge and issue a certificate (ACME or upload).
  3. Watch security events, tune with policies, and export a report.
