# VarmanWAF v0.22.0 — upstream sync round 1 (PingWAF v0.25.10 foundation)

**Release date:** 2026-10-13 · **Images:** `sovichetra/varmanwaf:0.22.0`,
`sovichetra/varmanwaf:latest` · **Tag:** `v0.22.0`

First upstream update round after the v0.21.x rollout: the foundation crates
are synced from PingWAF v0.20.0 to the latest upstream main (v0.25.10,
`aa597371`), plus the reconciled plugin hook. The full plan, crate mapping and
remaining batches live in [`docs/upstream-update-plan.md`](../upstream-update-plan.md).

## What this round brings

- **Client-IP spoofing hardening.** Forwarded headers (`X-Forwarded-For` /
  `X-Real-IP`) are only honoured when the direct TCP peer is loopback/private
  or a configured trusted proxy; a client arriving from a public address
  always resolves to its own address, so it can no longer forge the identity
  every IP rule keys on. `basic.trusted_proxies` (or the per-site trust model
  arriving with batch 2) configures public-address load balancers.
- **Host normalization.** `get_host` now strips ports (IPv6-aware), trailing
  dots and normalizes case, so site matching and rule lookups see one
  canonical host form.
- **Request-body plugin hook, upstream API.** Plugins can now inspect,
  rewrite or answer mid-body (`handle_request_body` returns
  `Option<HttpResponse>`); the proxy writes a plugin's response and aborts the
  upstream exchange. VarmanWAF's tail inspection uses this so a payload found
  beyond the inspection window now answers with the standard block page
  instead of a bare error; WebSocket tunnel findings still close the
  connection (no HTTP response is possible once upgraded).
- **Multi-node upstream fixes.** Upstream pool handling and lenient origin
  verification for snapshot-restored pools.
- **ACME robustness.** Ready-order acceptance, certificate reload no longer
  drops issued certificates, DNS provider fixes.
- **Config and proxy touch-ups.** Trusted-proxy configuration plumbing, error
  pages, and manager reload wiring.
- **Live-verification fix (this round's E2E):** large request bodies (> 64 KiB)
  could stall. The early body read could cross pingora's 64 KiB replay buffer
  mid-chunk, truncating the buffered replay so the upstream waited forever for
  the missing bytes. The read pass now consumes the whole body only when the
  declared `Content-Length` fits the replay window and exactly one chunk
  otherwise (the stream/tail inspection covers the rest), and a
  still-truncated replay is refused with an explicit 413 instead of stalling.

## Verification at release

- `cargo check --workspace --all-targets` clean; full test sweep green
  (engine 485, plugin 179, control-plane 215, agent 21, corpus 8,
  robustness 3, budgets 1, lane cost 1, shadow report 1); clippy
  `-D warnings` clean.
- Live end-to-end on the all-in-one stack:
  * benign 200; SQLi 403 with `sig.sqli.tautology | block`;
  * host normalization: `Host` with an explicit port, upper case and a
    trailing dot all route to the site (200);
  * client-IP trust: a spoofed `X-Forwarded-For` from a loopback peer is
    resolved and recorded (`198.51.100.7` in the event), while a public
    peer can no longer influence resolution;
  * large bodies: 64 KiB and below inherit the previous behaviour; bodies
    above the replay window no longer stall (chunked read + tail scan).

(batch 4), and the upstream feature branches (batch 5). Each batch ships
only when it compiles, passes the full suite and verifies live as a whole.
