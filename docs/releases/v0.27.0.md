# VarmanWAF v0.27.0 - Policy & Rule Control Plane, round 4 (P4: versions & apply)

**Release date:** 2026-10-13 • **Images:** `sovichetra/varmanwaf:0.27.0`,
`sovichetra/varmanwaf:latest` • **Tag:** `v0.27.0`

Round P4 of the Tiyi-informed control model: **policy history and
published-vs-applied honesty**. Every policy change is now an immutable
version that can be inspected, diffed and restored, and the dashboard shows
which nodes actually applied the published configuration.

## What this round brings

- **Policy versions** (`waf_policy_versions`): every create, field update,
  layer write or delete records an immutable snapshot — policy fields plus
  every layer payload — with a SHA-256 content hash (deduplicated against
  the latest version), the actor and the source (`api` / `rollback`).
- **History API**: `GET /policies/{id}/versions` (summaries with per-layer
  entry counts), `GET /policies/{id}/versions/{version_id}` (full snapshot)
  and `GET /policies/{id}/versions/diff?from=&to=` — a human-readable diff
  (changed fields; per layer: added/removed/changed entries, with rules
  keyed by name and overrides by their selector identity).
- **Rollback**: `POST /policies/{id}/rollback` restores a version's content
  as a **new revision** (history is append-only), records a `rollback`
  version and pushes the change to every assigned site. Layer writes now
  also accept `expected_revision` and return 409 on a stale value.
- **Applied-state reporting**: the bundle carries `policy_id` +
  `policy_revision`, the agent persists the revision of the last bundle it
  applied (survives restarts) and reports it on every heartbeat;
  `agents.policy_revision` stores it. `GET /sites/{id}/apply-status`
  returns the published hash/revision plus one row per serving agent with
  a state of `applied` (hash and revision match), `pending` (agent is
  fresh but has not caught up) or `unknown` (no fresh evidence) — a node
  that never reported is never assumed applied.
- **One consistent applied hash** (fix, found while E2E-verifying the
  apply-status): a full-config apply used to overwrite the agent's
  reported hash with the *SiteConfig* fingerprint while `SyncRules` delta
  sync and apply-status compare the *per-site bundle* fingerprint, so the
  dashboard could show `pending` for a node that was actually current.
  Every apply path now reports the bundle fingerprint (regression test).
- **Dashboard**: a **History** dialog in the policy editor (version list,
  diff against the previous version, restore button) and an **Apply
  status** card on the site Policy tab (published revision/hash, per-node
  applied revision with state badges).

## Verification at release

- `cargo test --workspace` green with new coverage: snapshot hashing is
  content-addressed; the version diff reports field and per-layer deltas
  (keyed rules/overrides, absent layers omitted); control-plane suite at
  320 tests; agent cache round-trips the new revision field; clippy
  `-D warnings` clean; `tsc -b && vite build` clean.
- Live E2E: a policy assigned to the E2E site was edited (layer added),
  diffed against the previous version, rolled back to the pre-edit
  version (probe behaviour flipped back), verified that the history gained
  a `rollback` entry and the revision bumped, that a stale
  `expected_revision` layer write returns 409, and that
  `/sites/{id}/apply-status` reports the published revision with the agent
  `applied` once the push lands.
