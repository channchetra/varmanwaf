# VarmanWAF v0.25.0 - Policy & Rule Control Plane, round 2 (P2: rule tuning)

**Release date:** 2026-10-13 • **Images:** `sovichetra/varmanwaf:0.25.0`,
`sovichetra/varmanwaf:latest` • **Tag:** `v0.25.0`

Round P2 of the Tiyi-informed control model: **rule tuning in data**. Rules
are no longer only on or off — a policy (or a site's overlay) can disable a
managed rule, downgrade it to monitor-only, or replace its anomaly score,
without touching the rule source.

## What this round brings

- **New policy layer kind `rule_overrides`**:
  `{ "overrides": [ { "rule_id": "VARMAN-1020", "action": "disable" } ] }`.
  Actions: `disable` (skipped entirely: no match, no score, no event),
  `monitor` (matched and recorded, never enforced), `score_override`
  (replaces the rule's anomaly contribution; the rule's own action still
  applies) and `default` (clears an override — meaningful in a site
  overlay). Entries are validated against the managed-rule catalogue, so a
  typo fails at write time.
- **Engine support**: `WafEngineConfig` gains `disabled_rules` and
  `rule_scores`; the evaluator skips disabled rules before expression
  evaluation and scores overridden hits with the explicit points value
  (new `AnomalyScorer::add_points_hit[_ex]`). Monitor/disable/score are
  mutually exclusive per rule.
- **Resolution and precedence**: the site's own `monitor_managed_rules`
  (or the policy's `crs` layer) is the base; policy `rule_overrides` apply
  on top; the site overlay wins last and can clear policy entries with
  `default`. The effective set is folded into the bundle
  (`disabled_rules`, `rule_scores`) and reported by
  `/sites/{id}/effective-config`.
- **Agent + protocol**: `WafConfig` carries the two new fields
  (`disabled_rules = 48`, `rule_scores = 49`); the agent's on-disk cache
  model defaults them for caches written before this release.
- **Custom-rule modes now reach the engine** (fix): a custom rule's `mode`
  was carried in the bundle but never wired into the engine
  (`monitor_custom_rules` was always empty), so a rule the dashboard showed
  as *monitor* still enforced its action — and re-armed the edge block on
  every hit. `monitor` rules are now recorded without enforcing and `off`
  rules are skipped entirely; a plugin regression test covers all three
  modes. (Found while E2E-verifying the rule-override layer.)
- **Dashboard**: the policy editor gains a **Rule tuning** tab — the
  managed-rule catalogue (id, name, tags, severity) with a per-rule action
  picker and a score field, plus a "N rules tuned" count; the site Policy
  tab's effective configuration now shows the disabled rules and score
  overrides that reach the site.

## Verification at release

- `cargo test --workspace` green with new coverage: engine tests for
  disabled rules (match/score/enforcement gone) and score overrides
  (aggregate drops by exactly the severity delta while the rule still
  blocks); plugin test proving the bundle fields reach the engine
  (block-mode control, disable removes the match, score override changes
  the total); control-plane tests for layer validation (unknown rule id /
  action, score required/forbidden), monitor-base precedence and overlay
  `default` clearing; clippy `-D warnings` clean; `tsc -b && vite build`
  clean.
- Live E2E: a policy on the E2E site tuned `VARMAN-1020` through every
  action — baseline event score 5, `disable` produces no event,
  `monitor` produces a monitor event, `score_override` produces a blocking
  event with score 1 — then the layer was removed and the default
  behaviour returned; config versions recorded throughout.
