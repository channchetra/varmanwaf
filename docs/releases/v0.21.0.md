# VarmanWAF v0.21.0 — first production rollout

**Release date:** 2026-10-08 · **Images:** `sovichetra/varmanwaf:0.21.0`,
`sovichetra/varmanwaf:latest` · **Tag:** `v0.21.0`

VarmanWAF is the production-grade, self-hosted, distributed WAF built on the
imported PingWAF platform: a Pingora data plane, a central control plane with
PostgreSQL, and the Varman detection engine (canonical model + detector
pipeline + native SecLang/CRS execution) running beside the inherited engine.

## Highlights

- **Engine switch, per site or process-wide** — `VARMAN_WAF_ENGINE=legacy|shadow|varman`
  plus the dashboard **Detection engine** selector. In `varman` mode the new
  pipeline enforces and can only *escalate* the legacy verdict, so
  dashboard-configured custom rules stay effective.
- **OWASP CRS conformance: 5150/5155 behavioural expectations (99.90%)** with
  the full 693-statement ruleset loading, measured against the official
  go-ftw corpus in-process at each rule's paranoia level; the five residuals
  are documented engine divergences with evidence
  (`docs/compatibility.md`).
- **19-detector pipeline** (fast lane + semantic lane): SQL, XSS, command,
  SSRF, NoSQL, SSTI, XXE, deserialization, prototype pollution, LDAP/XPath,
  GraphQL, JWT, DLP, JSON body-shape, threat intelligence, WebSocket
  handshake, protocol and signature checks — all corpus-ratcheted with benign
  guards.
- **Threat intelligence feeds** — bundled scanner/attack-tool starter feed,
  operator feeds via `VARMAN_WAF_TI_FILE`.
- **Virtual patching** — per-site SecLang rules validated by the control plane
  at upload and evaluated by the native engine at the edge.
- **OpenAPI request-shape validation** — per-site spec; undeclared
  operations, methods and missing required query parameters are recorded.
- **ATO defense** — failed-auth streaks on state-changing requests block the
  `(site, client)` pair with 403 + `Retry-After`.
- **External processors (Phase 9)** — UDS/TCP JSON contract with bounded
  contributions, monotonic merge, explicit failure policies and capability
  negotiation; reference implementation + compose profile included.
- **Engine telemetry** — shadow-comparison classes and processor outcomes
  ship with the heartbeat and render in the dashboard's agent detail.
- **Performance** — the pipeline inspects the corpus ~5× faster than the
  legacy engine (88 µs vs 446 µs per request; `docs/performance.md`).
- **Operations** — hot-reloadable site config, immutable per-site snapshots,
  structured security events, full access logs with body capture, auto-block
  of attacking IPs, retention controls.

## Verification at release

- 476 engine + 164 plugin + 215 control-plane + 21 agent unit tests; corpus,
  robustness, per-detector budget and lane-cost suites — all green; clippy
  clean (`-D warnings`).
- Live end-to-end on the all-in-one stack: benign traffic 200; SQLi/XSS/
  traversal/Log4Shell 403 (pipeline-verified events); scanner UA and `alg:none`
  JWT blocked; DLP and WebSocket shapes monitored; virtual patch and OpenAPI
  validation enforced per site; external processor block + failure-policy
  degradation; ATO streak block with `Retry-After`.

## Known limitations (documented, post-rollout)

- **Body inspection is windowed at the head** (`max_body_size`, default
  64 KiB): payloads beyond the window are not inspected unless the site sets
  `body_policy = "reject"` (413 above the limit). Tail-window inspection
  needs streaming inspection during forwarding.
- **WebSocket inspection covers the handshake** (cross-origin/CSWSH, body);
  frame-level inspection is post-rollout.
- **OpenAPI validation covers operations, methods and required query
  parameters**; JSON-Schema body validation is post-rollout.
- **ATO thresholds are process-level** (default 20 failures / 5 min → 5 min
  block; `0` disables); the tracker itself is per `(site, client)`.
- Five CRS corpus expectations remain documented divergences (see above).
- GitHub Actions is skipped for this account (billing); images are published
  manually as part of the release routine.

## Upgrade

```bash
docker compose pull
docker compose up -d
```

The control plane applies migration `000032` on start (virtual patches +
OpenAPI columns); no manual step is required.
