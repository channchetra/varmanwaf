# VarmanWAF v0.43.1 - Fix: a rollback records exactly one version, with the push's fingerprint

**Release date:** 2026-10-14 **Images:** `sovichetra/varmanwaf:0.43.1`,
`sovichetra/varmanwaf:latest` **Tag:** `v0.43.1`

A one-bug fix on top of v0.43.0 (the configuration-history console), found
by that release's live E2E before any image was published - the same
pattern as v0.35.0/v0.39.0. v0.43.1 carries the batch.

## The bug

Every console rollback produced **two** history entries and a fingerprint
that never matched the restored version:

- `config_history::rollback` recorded the rollback version with the
  **rule-bundle** fingerprint (`build_rule_bundle`), while the push path
  records the **full site config** fingerprint (`build_site_config`) -
  two different functions over (nearly) the same content, so the
  hash-based dedup in `record_version` could never match;
- the API handler then ran `touch_site` (bumping `site.updated_at` so
  agents re-pull even when the restore is a no-op) *after* that recording,
  changing the content the follow-up push fingerprints;
- the push therefore recorded a second version (`source=api`, attributed
  to the operator) moments later, and the history head was not the
  rollback version. Global-scope rollbacks recorded an empty fingerprint
  and had the same double-entry symptom.

## The fix

- `config_history` gained `restore` (snapshot restore only) and
  `record_rollback` (records the rollback version); `rollback` keeps the
  restore-and-record shape for the CLI.
- `config_hash_after` now computes **the push path's fingerprint** for
  both scopes (`grpc::site_config_hash` / `grpc::global_config_hash`,
  the latter over the same agent-visible site set the deployment-wide push
  builds from - resolution extracted into `resolve_visible_sites` so the
  two cannot drift).
- The console handler orchestrates **restore -> touch -> record -> push**:
  the rollback version is recorded synchronously with the post-touch
  fingerprint before the push spawns, so the push's detached recorder
  dedups against it. The response still reports the new version id.

## Verification at release

- `cargo fmt --all -- --check`, `cargo test -p varman-control` (348
  passed) and clippy `-D warnings` clean.
- Live E2E (config-history script, expectation updated): after a rollback
  the list head **is** the rollback version (`id == new_version`,
  `source=rollback`, actor = operator) - no follow-up `api` entry; the
  stored fingerprint differs from the pre-rollback head only through the
  site touch timestamp, as the E2E now states explicitly; the effective
  config still resolves and the viewer gate holds.
