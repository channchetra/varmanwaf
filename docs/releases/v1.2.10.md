# VarmanWAF v1.2.10 — refuse origins that point back at the WAF

**Release date:** 2026-10-27
**Images:** `sovichetra/varmanwaf:1.2.10`, `sovichetra/varmanwaf:latest`
**Tag:** `v1.2.10`

Safety patch for origin configuration after a production self-proxy loop.

## What happened

An origin pool was configured with `localhost:80`. Port 80 is the WAF's own
data-plane listener, so every request proxied to that “origin” arrived back at
the WAF and was proxied again. One manual **Test now** probe was enough to
start a recursive chain: 180k log lines in two minutes, 100% CPU, and status
499 lines for `asset.unitywork.space`.

The database already held the corrected origin (`10.1.18.5:3001`), but the
running data plane still used the old `localhost` node until it was restarted.
After the restart the loop stopped (0 probe lines, CPU 0.5%) and the site
served normally.

## The guard

- **API validation:** `normalize_origin_address` now rejects loopback or
  unspecified addresses on the WAF listener ports **80, 443, 9080 and 9090**
  (`localhost`, `127.0.0.0/8`, `::1`, `0.0.0.0`). A local app on another port
  (for example `127.0.0.1:3001`) is still allowed, as is a remote host on port
  80.
- **Probe guard:** **Test now** resolves the node first. If it resolves to a
  loopback/unspecified address on a listener port, the probe is refused with
  “origin points at the WAF listener; use the application's private address”
  and the node is marked unreachable — without opening a connection.
- Regression test: loopback listener addresses are rejected, while
  `127.0.0.1:3001`, `10.1.18.5:80` and a remote hostname on port 80 remain
  valid.

## Verification

- `cargo test -p varman-control --lib api::sites` → **11 passed**.
- Production after the manual restart: `asset.unitywork.space` via the WAF
  returns the application response, the loop log count is 0, and CPU is back to
  normal.

## Note

`asset.unitywork.space` still has HTTPS enabled but no certificate selected, so
`https://asset.unitywork.space/` cannot complete TLS yet. HTTP works. Issue or
select a certificate for that site separately.

## Upgrade

```bash
docker compose pull varman
docker compose up -d --force-recreate varman
curl -sk https://localhost:9080/api/v1/version   # -> 1.2.10
```

No migration and no configuration change. Existing valid origins are
unaffected.
