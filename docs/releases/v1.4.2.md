# VarmanWAF v1.4.2 — WebSocket stream inspection respects mode and action

**Release date:** 2026-11-02
**Images:** `sovichetra/varmanwaf:1.4.2`, `sovichetra/varmanwaf:latest`
**Tag:** `v1.4.2`

Fixes a false-positive WebSocket block that survived pausing or disabling a
policy.

## Root cause

`sem.cmd.command_context` is a **low-confidence** semantic rule whose action
is `Log` (score 5). The WebSocket stream inspector treated every finding as a
hard block and wrote `action=block, score=40`, regardless of:

- the finding's own action (`Log`/`Monitor` vs `Block`/`Challenge`);
- the site's protection mode (`monitor`/`off` vs `block`);
- the site's engine (`legacy`/`shadow` vs `varman`).

That is why `/ws` and `/cool/ws` on `office`/`uoffice` kept returning 403
after the policies were disabled. It was not a policy assignment; it was the
native stream inspector.

## Fix

- A stream finding now carries its pipeline action and score.
- Only `Block`/`Challenge` findings close a stream.
- Stream enforcement is enabled only for a **Block** site running the
  **Varman** engine; `monitor`/`off` and `legacy`/`shadow` record a monitor
  event instead.
- Tail-body inspection follows the same rule.
- Added regression tests:
  - `sem.cmd.command_context` (`id;`) is `Action::Log` / score 5.
  - `$(id)` escalates above `Log`.
  - `stream_enforcement` is false for monitor+Varman and Block+legacy, true
    only for Block+Varman.

## Verification

- `pingap-plugin`: 207 tests passed.
- `varman-control`: 420 tests passed.
- Root binary: 61 tests passed.
- Production verification after deploy: `/ws` and `/cool/ws` no longer return
  403; findings are recorded as `monitor` with the rule's real score.

## Upgrade

```bash
docker compose pull varman
docker compose up -d --force-recreate varman
curl -sk https://localhost:9080/api/v1/version   # -> 1.4.2
```

No new migration is required; migration 068 from 1.4.0 applies automatically.
