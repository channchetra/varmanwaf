# VarmanWAF v0.31.0 - CRS ruleset import with an honest catalogue

**Release date:** 2026-10-14 **Images:** `sovichetra/varmanwaf:0.31.0`,
`sovichetra/varmanwaf:latest` **Tag:** `v0.31.0`

R8 of the learning-pass program: OWASP CRS archives can now be imported
(GitHub release tag, direct URL or uploaded archive), inspected rule by
rule with file/line provenance, and bound to a policy so the rules this
engine can compile are enforced by the edge.

## What this round brings

- **Import sources.** `POST /api/v1/crs/import` accepts a GitHub release
  tag (`GET /api/v1/crs/releases` powers the picker), a direct `.tar.gz`
  URL, or an uploaded base64 archive. Every import stores the archive's
  SHA-256 fingerprint; importing the same archive again is idempotent and
  returns the existing ruleset instead of duplicating it.
- **Rules are parsed by this engine's own parser.** Each logical
  statement in `rules/*.conf` (multi-line continuations and `chain`
  members merged) is compiled with the same SecLang parser the data plane
  uses. The catalogue keeps, per rule: id, message, severity, paranoia
  level, attack category, phase and **file:line** provenance.
- **Nothing disappears silently.** A statement this engine cannot compile
  is stored as **unsupported with its parser error** - visible in the
  console and countable - and non-rule directives (`SecAction`,
  `SecRuleUpdateTargetById`, ...) are recorded as **directives**, not
  dropped. The ruleset header reports compiled / unsupported / directive
  counts, so "what did not make it" is never a guess.
- **Catalogue API and console.** `GET /api/v1/crs/rulesets/{id}` pages the
  catalogue with filters (category, paranoia level, phase, severity,
  keyword over id/message/file, compile status, statement kind). The
  console gains a **CRS rules** page: import dialog with a release picker,
  ruleset list with counts, and a catalogue browser showing each rule's
  provenance and, for unsupported rules, the parser error.
- **Binding is a policy layer.** The new `crs_import` layer
  (`ruleset_id`, optional paranoia ceiling, optional attack-category
  filter) compiles the supported rules into the **same SecLang source the
  edge already evaluates as virtual patches**; an explicit
  `virtual_patches` layer source still runs first. Filters are applied at
  compile time, and rules with no paranoia tag (setup rules) are always
  included unless a category filter excludes them.
- **The tester covers imported rules.** `POST /api/v1/policies/test`
  evaluates the bound ruleset exactly like the edge and lists "imported
  CRS rules" among the simulated sources, so a rule can be verified
  before the policy is applied.
- **Delete guards.** Deleting a ruleset is refused (409, with the binding
  count) while any policy layer references it - unbind first.

## Honest limits (by design)

- The engine implements a **subset** of the ModSecurity/CRS directive
  and operator surface. Real CRS 4.x imports therefore show exact
  compiled/unsupported/directive counts, and only compiled rules are sent
  to the edge. This round makes that split first-class instead of
  pretending full coverage.
- Rule tuning against imported ids works through the existing
  `rule_overrides` layer (ids appear in the catalogue and the compiled
  rule plan); CRS-specific tuning directives are recorded, not executed.

## Verification at release

- New unit tests: continuation/chain statement splitting, metadata
  extraction, supported vs unsupported classification, tar.gz extraction
  (one rules file kept, non-rules files skipped), fingerprint stability,
  and `crs_import` layer validation (bad uuid, out-of-range paranoia
  ceiling, unknown keys).
- `cargo test --workspace` green (control-plane suite grows by four CRS
  tests); clippy `-D warnings` clean; `tsc -b && vite build` clean.
- Live E2E: a synthetic CRS archive is imported through the API; the
  catalogue reports its exact compiled/unsupported/directive split with
  file:line; a policy binds the ruleset through `crs_import`; the
  **tester** flags the sample request as blocked and the edge itself
  answers **403** for the matching path and 200 for benign traffic;
  the delete guard refuses while bound; everything is cleaned up after
  the probe.
