# VarmanWAF v0.30.0 - One home for protection, and a rule tester

**Release date:** 2026-10-14 • **Images:** `sovichetra/varmanwaf:0.30.0`,
`sovichetra/varmanwaf:latest` • **Tag:** `v0.30.0`

Two answers to operator confusion and to "how do I know it works before I
apply it": the policy surface now lives where protection lives, and a
**rule tester** evaluates a sample request against the exact native engine
configuration the edge would receive.

## What this round brings

- **Protection is the single home.** The per-site Policy surface moved
  from its own top-level tab into **Web Protection** (tabs: Grading /
  WAF Rules / CC Protection / **Policy**). Old `/sites/{id}/security/policy`
  links redirect to the policy tab, and the duplicate sidebar entry is
  gone. When a site follows a policy, every other protection tab shows a
  banner: *"This site follows policy X (rev N). The policy overrides the
  settings on this page; local deltas belong in the site overlay."* — so
  the two layers can no longer be mistaken for competing places to edit
  the same thing.
- **Rule tester** — `POST /api/v1/policies/test` evaluates one sample
  request (method, path, query, headers, body, client IP, host) against
  the exact configuration the edge would receive: managed rules with
  monitor/disable/score overrides and target exclusions, policy and site
  custom rules, and SecLang virtual patches. The result names the
  verdict, the score, every matched rule **with its source** (managed /
  policy / site / patch) and flags tuned hits; notes list the tuning that
  applied.
- **Draft testing**: the rule tuning tab's **Test draft** button tests
  the layer draft as if it were saved (no publish needed), and the tester
  is also available from the policy editor toolbar (saved config) and the
  site's effective-configuration card.
- **No fake certainty**: the tester reports what it does **not**
  simulate — rate limits, IP/geo access and bot checks are edge decisions
  that depend on request history — instead of guessing an answer.
- **Learning pass recorded**: `tiyi-analysis/logs-alerts-crs.md` documents
  the studied product's CRS import flow (GitHub release tag/archive,
  fingerprint, rule catalogue with file:line, per-rule overrides) and its
  alert model (rules with ratio thresholds and minimum samples, channels,
  silences), with the plan for our next rounds (R8 CRS import, R9 log
  provenance + threshold alerts + "why was this blocked" resolver).

## Verification at release

- `cargo test --workspace` green (control-plane suite grows with three
  tester tests: a policy rule blocks its path and passes clean traffic;
  monitor tuning is visible in the result and in the notes; a SecLang
  patch escalates the verdict and a broken patch is reported instead of
  skipped). Clippy `-D warnings` clean; `tsc -b && vite build` clean.
- Live E2E: the tester's verdicts are compared against the edge itself —
  a policy rule that the tester says blocks answers **403** once applied,
  a draft override that the tester says disables a managed rule produces
  no event live, and a draft SecLang patch that the tester says blocks a
  path blocks it live.

## Next rounds (from the learning pass)

- **R8** — CRS ruleset import (GitHub release tag or archive upload,
  fingerprint, rule catalogue with file/line and filters, per-rule
  overrides against imported ids, impact preview).
- **R9** — event provenance (`file:line`, category, phase) with a "why was
  this blocked" resolver across IP block → rate limit → WAF rule →
  policy layer, plus alert rules with ratio thresholds/minimum samples,
  channels and silences.
