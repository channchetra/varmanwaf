# VarmanWAF v0.60.1 - Import fix: the range removal form

**Release date:** 2026-10-15 **Images:** `sovichetra/varmanwaf:0.60.1`,
`sovichetra/varmanwaf:latest` **Tag:** `v0.60.1`

v0.60.0 was tagged in git but its image was never published: the live
import E2E refused the real WordPress plugin on the one directive form the
recon had not seen. Operators get the fix in the **0.60.1** image.

## What the live run found

The plugin's disable switch uses a **range**:
`ctl:ruleRemoveById=9507100-9507999`. Our parser accepted single ids only,
and since unknown/invalid ctl ops are refused at parse time, the import was
rejected with `ctl:ruleRemoveById id "9507100-9507999" is not a number` -
exactly the honest refusal the design intends, caught before anything was
stored.

## What this round changes

- **`ctl:ruleRemoveById` accepts ranges**: a new `RemoveByIdRange(from, to)`
  ctl op, stored per transaction and consulted by `is_rule_removed`
  alongside the single-id set. (The exclusion-plugin forms -
  `ctl:ruleRemoveTargetById=<id>;<target>` and the by-tag variant - were
  already supported in v0.60.0.)
- **A test pins the semantics**: a range removes every rule inside it while
  rules outside still fire, and a `ruleRemoveTargetById` suppresses the
  named target for one rule id while other rules keep matching.
