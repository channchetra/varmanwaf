# VarmanWAF v0.39.0 - Batch 4a: account & identity in the console

**Release date:** 2026-10-14 **Images:** `sovichetra/varmanwaf:0.39.0`,
`sovichetra/varmanwaf:latest` **Tag:** `v0.39.0`

Upstream batch 4 begins: the dashboard gains the account surfaces the
control plane has supported all along but the console never exposed.

## What this round brings

- **Dashboard users** (Settings → Dashboard users, admin only): create
  accounts with a role (administrator / auditor / viewer), edit names,
  rename the login name, disable and re-enable accounts, and see each
  account's **most recent login with its source IP** - resolved server-side
  from the login history. The UI mirrors the server's self-lockout guards
  (an admin cannot disable or downgrade themselves, and the last enabled
  administrator always survives) instead of duplicating them: the controls
  are simply not offered for one's own role.
- **First-sign-in password gate**: a non-dismissible dialog blocks the
  console while `must_change_password` is set (accounts created by an
  administrator). It replaces the password, refreshes the session profile
  and disappears; the server keeps rejecting writes until then anyway, so
  the dialog states the reason instead of hiding it.
- **Login-name change** in the account card: changing the e-mail requires
  the current password and revokes every outstanding token (the token's
  e-mail claim goes stale) - both behaviours were already enforced by the
  server; the form now surfaces them, and successful changes are recorded.
- Types/APIs ported from upstream: `users` (list/create/update), the
  extended `User` shape (`must_change_password`, `disabled`, `last_login_*`)
  and the extended `UpdateProfileRequest` (`email`, `current_password`).
- The `auditor` role joins the role labels in the console.

## Verification at release

- `tsc -b && vite build` clean; every new surface verified present in the
  built bundle; the Rust side carries the version bump (all suites re-run
  green, clippy clean).
- Live E2E against the real API contract the UI depends on: an
  administrator creates an auditor account; the new account signs in with
  `must_change_password: true`; replacing the password clears the flag and
  **revokes the old token** (401); the admin list shows the account with its
  last login and IP; a role change revokes the token immediately; disabling
  refuses sign-in and re-enabling restores it; cleanup disables the E2E
  account (accounts are disabled, not deleted - that is the endpoint's
  contract).
