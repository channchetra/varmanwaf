# VarmanWAF v0.24.0 - Policy & Rule Control Plane, round 1 (P1)

**Release date:** 2026-10-13 • **Images:** `sovichetra/varmanwaf:0.24.0`,
`sovichetra/varmanwaf:latest` • **Tag:** `v0.24.0`

Round P1 of the Tiyi-informed control model: **WAF policies**. A policy is a
named, revisioned, layered document shared by sites; a site either follows one
policy (with a sparse per-site overlay) or keeps its own settings, so nothing
changes until a policy is assigned.

## What this round brings

- **Schema** (migration `000053`): `waf_policies` (name, description, enabled,
  monotonic `revision`), `waf_policy_layers` (one typed document per
  `(policy, kind)`, validated JSONB), `site_waf_policies` (one policy per
  site), `site_waf_policy_overrides` (sparse per-site deltas).
- **Layer kinds** (`policy` module): `engine` (switch, mode, paranoia level,
  advanced mode, engine selection, monitor-only categories/stacks), `crs`
  (managed-rule monitor list) and `custom_rules` (ordered reusable rules).
  Unknown kinds and unknown keys are **rejected at write time** — a typo fails
  loudly instead of silently never applying.
- **Resolution precedence**: `site overlay > policy layer > the site's own
  settings`. A site with no assignment (or a deleted/disabled policy) builds
  exactly the same bundle it did before, proven by a regression test.
- **Bundle integration** (`grpc::config`): assigned sites get the effective
  engine/CRS posture applied over their row, and policy custom rules are
  merged into the site's rule set with namespaced ids
  (`policy:<policy-id>:<index>`); the config fingerprint therefore covers
  policy edits and agents resync when a policy changes.
- **REST APIs**: policy CRUD (`/policies`, optimistic `expected_revision`,
  409 on conflict), layer upsert/delete (`/policies/{id}/layers/{kind}`),
  site assignment (`/sites/{id}/policy`), per-site overlay
  (`/sites/{id}/policy-override`) and the resolution preview
  (`/sites/{id}/effective-config`). Policy edits mark every assigned site
  for re-sync and push the new bundle to connected agents.
- **Site mode now caps every engine path** (fix): with `engine_mode=varman`
  the site's `mode` only capped the legacy engine, so a `monitor` site could
  still be blocked by the pipeline (and an `off` site could still be blocked
  too). The mode is now applied to the escalated verdict — `monitor`
  downgrades Block/Challenge to a recorded Monitor event, `off` skips
  inspection entirely — so the mode shown in the dashboard is authoritative
  no matter which engine (legacy, pipeline, custom layers, external
  processor) produced the finding.
- **Dashboard**: a **Policies** page (list, create, editor with Engine /
  CRS tuning / Custom rules tabs), a site **Policy** tab (assignment,
  overlay editor, effective configuration preview with per-knob values and
  the policy rules that reach the site), sidebar entries and i18n keys.

## Verification at release

- `cargo test --workspace`: **1552 passed, 0 failed, 2 ignored** (control
  plane grows with the policy suite: layer validation, unknown
  kinds/keys/values, typed-view dedupe, resolution precedence and the
  bundle builder's policy application; the plugin adds the site-mode cap
  regression: block-mode control, monitor-mode cap); clippy
  `--workspace --all-targets -D warnings` clean; `tsc -b && vite build`
  clean.
- Live deploy + E2E (all-in-one image): the E2E site's own `monitor` mode
  answered the union-select probe **200** (the mode-cap fix; previously
  403); assigning a policy with an `engine {mode: block}` layer flipped the
  same probe to **403** (`stage1-critical: SQL-001`); a `custom_rules`
  layer blocked its path with **403** (`likely-clean: policy:<id>:0`); a
  site override `engine {mode: monitor}` capped policy + rule back to
  **200** with Monitor events recorded (overlay precedence + cap); clearing
  the override restored **403**; clearing the assignment returned the site
  to its baseline **200**. Every push recorded a configuration version,
  and cleanup left no policies, assignment or edge blocks behind. The
  dashboard bundle is embedded and serving (`/policies` SPA route plus the
  new page markers in the shipped JS); a full browser session was not run
  because the control plane presents a self-signed certificate.

## Not in this round (P2-P6 of the plan)

Per-rule overrides with actions (disable / log-only / monitor / score
override) and the dashboard rule browser (P2); target exclusions, tag/severity
selectors and the compile preview (P3); policy versions, diff, rollback and
per-node applied-revision reporting (P4); templates and recipes (P5);
remaining layers (body, api_schema, ip_access, rate_limit, bot, logging) and
the full overlay UI (P6). See `tiyi-analysis/varmanwaf-policy-design.md`.
