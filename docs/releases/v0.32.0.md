# VarmanWAF v0.32.0 - "Why was this blocked?", and alerts that cannot be fooled by one probe

**Release date:** 2026-10-14 **Images:** `sovichetra/varmanwaf:0.32.0`,
`sovichetra/varmanwaf:latest` **Tag:** `v0.32.0`

R9 of the learning-pass program: security events now explain themselves,
and threshold alert rules watch them with ratio conditions that require a
minimum sample count - so a single blocked probe in a quiet minute cannot
page anyone.

## What this round brings

- **"Why was this blocked?"** - `GET /api/v1/security-events/{id}/why`
  resolves the decision chain behind one stored event from what the control
  plane can actually prove:
  - the event itself (decision, verdict, score, request),
  - automatic IP-block state for the client (with reason and expiry),
  - whether a rate-limit rule or bot/challenge produced the event,
  - **the producing rule, with its source**: a built-in managed rule
    (catalogue lookup), an **imported CRS rule with ruleset, file and line**
    (`virtual-patch:<id>` resolved through the R8 catalogue), a policy layer
    rule (`policy:<uuid>:<n>` / `:rl:` / `:ip:`), or a site custom rule,
  - the site's current policy binding (with a note when the binding changed
    after the event, so the shown policy is never silently assumed to be the
    one that served the request),
  - the tuning that applies to that rule (disable / monitor / score change).
  - What cannot be determined is listed under **"what could not be
    determined"** - older rows without an event type, missing rule ids,
    ids no catalogue carries - never guessed.
- **Alert rules** - `/api/v1/alerts/rules`: two metrics over a sliding
  window (60s - 24h):
  - `event_count` - matching security events (site, event type and
    rule-id-substring filters),
  - `blocked_ratio` - blocked events as a percentage of requests seen in
    the same window, gated by **minimum samples** (the studied product's
    "minimum N samples" lesson: a quiet window cannot fire).
  - Cooldowns, per-rule severity, optional channel binding (empty = every
    channel subscribed to `security.alert`), and per-rule last observation
    (`last_value`, `last_samples`, `last_fired_at`) so the console shows
    what the last evaluation actually saw.
- **Preview, honestly** - `POST /alerts/rules/{id}/preview` evaluates the
  rule right now and reports value, hits, samples, threshold and whether it
  would fire - **dispatching nothing** - plus whether an active silence is
  muting it and what the sample denominator is (requests, not events).
- **Silences** - `/api/v1/alerts/silences`: maintenance windows, global or
  per site, with reason and author. A firing rule inside a silence is
  logged (`met its threshold inside a silence; not firing`), never sent.
- **Alerts console** (`/alerts`): rules table with live conditions and last
  observations, one-click preview, silences, the **notification channels**
  (e-mail / WeCom / DingTalk / webhook - full CRUD, test button, event
  subscriptions) and the dispatched-alert history. Every dispatch is
  recorded in the history **even when delivery fails**, so "nothing was
  sent" can never masquerade as "nothing happened".
- **Logs integration**: the security-event dialog has a "Why was this
  blocked?" panel that renders the resolved chain step by step.

## Design notes

- The evaluator is a 30-second tick over stored events - it is not inline
  in the request path, and it says so. Ratio denominators come from
  `access_logs` (requests the agents actually shipped), stated in the
  preview response as `samples_basis`.
- Every mutation is admin-gated and logged with its actor; silences record
  who created them.
- The `security.alert` event type joins the channel subscription list, so
  existing alert sources (certificates, agents, control-plane resources)
  and security rules share one delivery system.

## Verification at release

- New unit tests: threshold math per metric (count at threshold; ratio
  gated by minimum samples - a 100 % ratio with one sample does not fire),
  non-finite thresholds never fire, channel-id parsing skips invalid
  entries, and the R8/R9 migrations stay in the chain.
- `cargo test --workspace` green; clippy `-D warnings` clean; `tsc -b &&
  vite build` clean.
- Live E2E: a real managed-rule block and a real imported-CRS block are
  produced through the edge; the alert rule fires on the evaluator tick and
  its row records the observation; the preview reports `would_fire` without
  dispatching; a silence flips the preview to silenced; the resolver shows
  the managed rule, the CRS ruleset **with file:line**, the bound policy and
  the auto-block state; everything is cleaned up afterwards.
