# VarmanWAF v0.44.0 - Telegram alert channel + administrator password reset

**Release date:** 2026-10-14 **Images:** `sovichetra/varmanwaf:0.44.0`,
`sovichetra/varmanwaf:latest` **Tag:** `v0.44.0`

Two operator asks in one round: Telegram joins the alert channels, and user
management gains the missing administrator action - setting a temporary
password. (The full report generator lands next, as its own round.)

## Telegram alert channel

- **New channel kind `telegram`**: bot token + chat id, delivered through
  the fixed `api.telegram.org` host (`/bot<token>/sendMessage`, plain-text
  messages so MarkdownV2 escaping can never reject an alert).
- **The bot token is a sealed secret**: it joins the sealed/redacted key
  set (`smtp_pass`, `secret`, `secret_token`, `bot_token`), so it is
  encrypted at rest and comes back as `__REDACTED__` in every response.
- **Token-leak hardening**: the token travels in the URL path, so transport
  errors are stripped of the URL (`err.without_url()`) before they reach
  logs or the test-channel response, and the reply body is never echoed
  (the same SSRF-read rationale as the generic webhook).
- Console: the Alerts channel editor gains the kind and its two fields with
  honest hints (where the token comes from, how to read a chat id).
- Validation rejects a telegram channel without `bot_token`/`chat_id` at
  creation time, like the other kinds.

## Administrator password reset

- **`POST /api/v1/users/{id}/reset-password`** (admin only): sets a
  temporary password, forces the first-sign-in change and bumps the token
  version, revoking every outstanding session. Resetting one's own password
  is refused - that stays on `/auth/password`, where the current password
  is required; this route must not become a self-service bypass.
- Console: a key action on each other user's row opens a reset dialog with
  the password rules and the consequences spelled out (forced change, all
  sessions revoked, user not notified - tell them out of band).
