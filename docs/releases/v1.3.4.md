# VarmanWAF v1.3.4 — Per-site mode changes reach the edge

**Release date:** 2026-10-30
**Images:** `sovichetra/varmanwaf:1.3.4`, `sovichetra/varmanwaf:latest`
**Tag:** `v1.3.4`

Follow-up to v1.3.3. Block and Monitor changes now invalidate the right site.

## Why

The WAF plugin compiles one `SiteContext` per domain and caches it. It keyed
that cache on `agent.config_hash()`, which is the **first** site's rule-bundle
hash, not the current site's. Changing the mode or rules of any other site
left its context pinned to the old configuration. The dashboard correctly
reported `block` from the database while the edge kept running `monitor`.

v1.3.3 fixed the paused path by reading `sites.status` from the live rule
cache. The matrix test then exposed this broader keying bug: after the service
was warm, setting a non-first site to Block still let the SQLi probe through.

## Fix

- `SiteRules` now carries the per-site bundle `config_hash`.
- The plugin's per-domain context cache compares against that site's hash.
- Caches written before the field existed fall back to the global hash.

Paused status remains a live read, so a pause still applies without waiting
for a context rebuild.

## Upgrade

```bash
docker compose pull varman
docker compose up -d --force-recreate varman
curl -sk https://localhost:9080/api/v1/version   # -> 1.3.4
```

No migration is required. Sites configured through the dashboard keep their
current mode; the edge applies it correctly after this update.
