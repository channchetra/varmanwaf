# VarmanWAF v1.1.2 - IP-group edit crash, runtime ACME issuance, SSL reasons

**Release date:** 2026-10-17 **Images:** `sovichetra/varmanwaf:1.1.2`,
`sovichetra/varmanwaf:latest` **Tag:** `v1.1.2`

Two production bugs fixed, both reported from a live deployment, plus the SSL
surface now says *why* an order failed instead of leaving a bare status.

## What this round fixes

- **IP groups: editing a group and unchecking "Apply globally (all sites)"
  crashed the console** (React error #301, "Maximum update depth exceeded").
  The group's site selection was seeded with `setState` inside React Query's
  `select`, so every render pass re-triggered it. The seeding now happens
  during render, once per group - the same pattern used elsewhere in the
  console. Reproduced on the deployed build, verified fixed in the dev build
  (no error, the site picker appears).
- **ACME certificates created while the process runs never started
  issuance.** The data-plane assembly registered the Let's Encrypt background
  task only when the *start-up* configuration already contained certificates,
  so a certificate created later (console or API) was written into the live
  configuration but nothing ever processed it: the row stayed `pending` and
  the stale sweeper failed it 30 minutes later with a generic reason. The
  task is now always registered (unless `PINGAP_DISABLE_ACME` is set); it
  re-reads the live configuration each cycle, so runtime-created orders are
  picked up within the ACME cycle.
- **SSL surfaces state the reason.** The global SSL page and the site's
  SSL/TLS tab now render `failure_reason` under the status badge (with the
  full text on hover) and show a pending hint that points at the Application
  log - which carries the raw `pingap::acme` log lines as certificate events.
- **The raw ACME log now reaches the right certificate.** The capture layer
  kept only the tracing *message* and dropped the fields - but the ACME crate
  names the identifiers in a field (`domains="a.example.com,…"`), so ship-time
  attribution could not match a domain and every raw line landed
  unattributed: the per-certificate log stayed empty and only the global
  event list showed anything. Captured lines now carry their fields (bounded),
  so the Application log shows the real transcript per certificate. Covered by
  a regression test.
- **A certificate selection can be cleared, and deleting a certificate clears
  a dangling selection.** `PUT /sites/{id}/ssl-settings` could not clear
  `certificate_id` (a JSON `null` was indistinguishable from an omitted field),
  so a site whose certificate had been deleted kept pointing at the dead row -
  which also made raw ACME lines attribute to a ghost. The field now
  distinguishes "absent" (leave it) from "explicitly null" (clear it), and the
  delete handler clears the selection when it referenced the deleted
  certificate, recording a `posture_cleared` event. Covered by a regression
  test.

## Verification at release

- Crash: reproduced on 1.1.1 (edit → uncheck → "Unexpected Application
  Error", React #301) and verified fixed (dev build: no error, picker shown).
- ACME: after the fix, a certificate created at runtime is processed by the
  ACME task - the edge logs the Let's Encrypt account creation and the order
  attempt, and the raw transcript lands in the certificate events, attributed
  to the certificate (verified locally end to end; the ACME cycle runs every
  10th 60-second tick, so an order is picked up within ~10 minutes).
- Console gate: tsc clean, eslint 0 errors, vitest passing; Rust workspace
  builds; the cert-events regression test passes; full E2E sweep (42 scripts)
  on the deployed build.
- Production diagnostics used: the sweeper's `issuance_failed` event and
  `failure_reason` (both present and correct), plus DNS/port-80 checks.
