# VarmanWAF v1.4.5 — no duplicate ACME orders on restart

**Release date:** 2026-11-27
**Images:** `sovichetra/varmanwaf:1.4.5`, `sovichetra/varmanwaf:latest`
**Tag:** `v1.4.5`

Stops a restart (or an unrelated config reload) from ordering a duplicate
control-plane certificate.

## Why

The data-plane config is rebuilt from scratch on every restart and reload,
and its `__management` entry started with no PEM material. The ACME task
reads the certificate from that config: an empty pair means "nothing issued
yet", so it ordered a fresh certificate. Four duplicate certificates were
issued on 2026-11-27 (03:53, 04:40, 04:43, 04:58) against Let's Encrypt's
limit of five per week. A fifth restart would have consumed the last slot and
the 2026-12-01 renewal would have been refused, expiring the certificate on
2026-12-03.

## Fix

- `management_cert::set_seed` records the pair the listener already serves;
  `load_active_certificate` and `store_and_activate` update it for ACME
  certificates.
- `build_pingap_config` seeds `__management` with that pair, so the ACME task
  sees a valid certificate and does not order a replacement.
- The seed is deliberately not applied to uploaded or self-signed pairs: if
  ACME is armed but a different certificate is active, an order is correct.

`varman-control/src/management_cert.rs`,
`varman-control/src/api/system_tls.rs`, `src/varman.rs`.

## Verification

- `varman-control`: 424 tests, clippy clean.
- Production: after the 1.4.5 restart, `control_plane_certificates` must gain
  **no new row** and the listener must keep fingerprint `1db2ddbc…`
  (`notAfter` 2026-12-03 20:58 UTC).

## Rate-limit note

Do not trigger further ACME orders before **2026-12-04 03:53 UTC**, when the
2026-11-27 batch leaves the seven-day window. The 2026-12-01 renewal is the
fifth and must succeed.

```bash
docker compose pull varman
docker compose up -d --force-recreate varman
curl -sk https://localhost:9080/api/v1/version   # -> 1.4.5
```
