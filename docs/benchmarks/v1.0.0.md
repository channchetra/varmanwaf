# VarmanWAF 1.0.0 Performance Benchmark

**Measured:** 2026-10-16 · **Build:** `sovichetra/varmanwaf:1.0.0` (deployed
all-in-one container: control plane + edge agent + Pingora data plane) ·
**Harness:** `build-artifacts/run-benchmark.ps1` + `build-artifacts/bench.js`
(raw results: `build-artifacts/bench-results.json`)

## What was measured

| Lane | Request | What the number includes |
| --- | --- | --- |
| Pass-through | `GET /` → 200 | Full edge path: HTTP in, WAF pipeline (allow verdict), proxy to the origin, response out |
| Engine block (dotfile) | `GET /.env?bench-block=1` → 403 | A fresh engine decision per sample: canonicalization, signature lane, managed rules, custom rule, block page |
| Engine block (SQLi) | `GET /?id=1' OR '1'='1&bench-block=2` → 403 | Same, with a payload that exercises the SQLi detectors |
| Refusal lane | `GET /.env?bench-block=1` → 403 | The 600s auto-block window: the edge drops the request before the engine runs |
| Control plane | REST API GETs | Axum + PostgreSQL round trips over HTTPS |

## Methodology (and what it deliberately accounts for)

- **Block verdicts are measured on the engine, not the refusal lane.** A block
  verdict opens a 600s edge refusal window for that client IP, and the
  control-plane unblock only reaches the edge once the auto-block row exists
  (row creation lags the verdict). The engine phases therefore run from a
  small generator container on the varman network with a range of source
  addresses, one fresh address per sample - every sample is a real engine
  decision. Each address gets an unmeasured warm-up request first (the first
  packet from a freshly added address stalls on neighbour discovery).
- **The site's posture.** The measured site (`e2e.varman.local`) carries its
  real deployed configuration; its managed rules run in **monitor** posture.
  The block phases temporarily switch the site to **block** posture and add a
  temporary operator block rule (the same pattern the E2E scripts use), then
  restore the prior posture and delete the rule. Without an enforcing
  posture a "block path" measurement would be fiction.
- **Warm-up gates.** Every phase waits until the expected status is actually
  served before the timed run, so a config reload (rule push, posture change)
  cannot contaminate the samples.
- **Requests carry a User-Agent** (the generator identifies itself). The bot
  layer challenges requests without one - the challenge page is served with
  `503` by design - which is a product behaviour, not a benchmark failure.
- **Keep-alive** connections; latency measured per request around the full
  request/response; percentiles over all samples in the phase.

## Environment (honest caveats)

- One Windows development machine running Docker Desktop. The control plane,
  the edge agent, PostgreSQL and the origin all share its CPU; the origin is
  `nginx:alpine` on the same bridge network, so the pass-through number
  includes a local Docker network round trip, not a WAN upstream.
- No tuning of any kind (no CPU pinning, default Docker networking, default
  PostgreSQL settings). **These are relative numbers, not capacity
  guarantees.**
- The load generator is Node.js 24 (single process, keep-alive agent); at
  100 connections the generator itself is part of the measurement.
- The site runs its real state (CRS import, policies, rules), not a stripped
  bench fixture.

## Results

### Data plane - pass-through (`GET /`, full WAF + proxy)

| Concurrency | Requests | Throughput | p50 | p95 | p99 | max |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 1,000 | **1,450 req/s** | 0.62 ms | 0.91 ms | 1.49 ms | 3.11 ms |
| 25 | 3,000 | **5,835 req/s** | 4.10 ms | 6.20 ms | 8.53 ms | 21.67 ms |
| 100 | 3,000 | **5,485 req/s** | 16.96 ms | 22.56 ms | 71.28 ms | 77.03 ms |

All 7,000 requests returned 200; zero errors. The c=25 run is the throughput
sweet spot on this machine (the generator becomes a bottleneck at c=100,
which is why throughput plateaus while latency grows).

### Data plane - WAF block verdicts (engine path, 403)

| Lane | Samples | p50 | p90 | p95 | p99 | mean |
| --- | --- | --- | --- | --- | --- | --- |
| Dotfile probe (`.env`) | 40 (all 403) | **1.17 ms** | 1.25 ms | 1.29 ms | 2.02 ms | 1.19 ms |
| SQLi query payload | 40 (all 403) | **0.85 ms** | 0.90 ms | 1.00 ms | 1.04 ms | 0.86 ms |

The block decision plus the block page costs ~1 ms on top of the
pass-through path - and a block avoids the upstream round trip entirely, so
a blocked request is answered *faster* than an allowed one.

### Data plane - auto-block refusal lane (600s window)

| Requests | Throughput | p50 | p95 | p99 | max |
| --- | --- | --- | --- | --- | --- |
| 2,000 (c=25, all 403) | **9,836 req/s** | 2.01 ms | 4.99 ms | 10.21 ms | 19.53 ms |

The refusal lane skips the engine and the upstream entirely; it exists to
make repeat attacks cheap to refuse.

### Control plane - REST API (sequential, HTTPS)

| Endpoint | Samples | p50 | p95 | p99 | max |
| --- | --- | --- | --- | --- | --- |
| `GET /version` (no auth) | 200 | 0.50 ms | 0.70 ms | 0.84 ms | 1.15 ms |
| `GET /sites` | 50 | 1.15 ms | 2.24 ms | 2.36 ms | 2.36 ms |
| `GET /sites/{id}/blocked-ips` | 50 | 1.67 ms | 2.52 ms | 2.99 ms | 2.99 ms |
| `GET /policies` | 50 | 1.22 ms | 1.95 ms | 3.07 ms | 3.07 ms |
| `GET /logs/security?limit=50` | 30 | 1.79 ms | 2.21 ms | 2.42 ms | 2.42 ms |
| `GET /logs/access?limit=50` | 30 | 7.00 ms | 8.21 ms | 8.43 ms | 8.43 ms |
| `GET /sites/{id}/api-assets` | 30 | 15.43 ms | 16.57 ms | 19.41 ms | 19.41 ms |
| `GET /analytics/summary` | 50 | 18.62 ms | 20.53 ms | 256.34 ms | 256.34 ms |

All API responses were 200 with zero errors. Notes:

- `/analytics/summary` is the heaviest read (fleet + traffic aggregation);
  its p99 shows one 256 ms outlier - a single sample on a shared desktop,
  visible here rather than hidden.
- `/logs/access` and `/api-assets` are heavier than plain resource reads
  (pagination over the access-log pipeline and the observed-endpoint
  aggregation respectively) and still stay well under 20 ms.
- Everything else answers in single-digit milliseconds.

## Reading the numbers

- **p50 vs p99** - the tail spread at higher concurrency reflects Docker
  Desktop scheduling and the single-process generator, not the WAF; on a
  tuned server the tail compresses.
- **Block is cheaper than allow** - a block verdict avoids the upstream trip;
  the engine decision itself costs ~1 ms.
- **Refusal lane is cheapest** - by design: no engine, no upstream.

## Reproducing

```powershell
cd build-artifacts
pwsh -NoProfile -File .\run-benchmark.ps1          # add -KeepOrigin to keep the nginx origin
```

The script starts its own origin container, switches the site to block
posture for the block phases and restores it, cleans up auto-blocks, removes
the temporary rule and the generator/origin containers, and writes
`build-artifacts/bench-results.json`.
